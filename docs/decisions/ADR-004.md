# ADR-004: RLS Deny-All for alembic_version, Grants-Based Exposure Control for spatial_ref_sys

> Date: 2026-08-12
> Status: Accepted

## Context

Supabase Security Advisor reported two CRITICAL findings (`0013_rls_disabled_in_public`):

1. `public.alembic_version` — Alembic's internal migration-version table.
2. `public.spatial_ref_sys` — PostGIS extension metadata (EPSG/SRID definitions).

Audit findings (replicated the advisor lint query against the live DB):

- Both tables have RLS disabled and **zero policies**.
- Supabase default privileges (`ALTER DEFAULT PRIVILEGES ... GRANT ALL ... TO anon, authenticated, service_role`) granted **full CRUD (`arwdDxtm`) to `anon` and `authenticated`** on both tables.
- Both tables are **reachable through the PostgREST Data API with the anon key** — `GET /rest/v1/alembic_version` and `GET /rest/v1/spatial_ref_sys` both returned HTTP 200. `alembic_version` is therefore publicly writable: an attacker could DELETE rows or rewrite the version, breaking future migrations.
- `spatial_ref_sys` is owned by `supabase_admin` (extension-created), not by the application.
- PostGIS functions that read `spatial_ref_sys` (`st_transform`, `addgeometrycolumn`, `get_proj4_from_srid`, `updategeometrysrid`) are **SECURITY INVOKER** (`prosecdef = false`).
- The backend connects as the `postgres` superuser (`rolbypassrls = true`); `service_role` also bypasses RLS. Neither is affected by RLS or table grants. The frontend uses supabase-js for **auth only** (no PostgREST `.from()`/`.rpc()` calls).

## Decision

**`public.alembic_version`** — enable RLS with **zero policies** (deny-all for `anon`/`authenticated`) and additionally `REVOKE ALL` from `anon`/`authenticated` as defense in depth. This is the Supabase-documented fix for internal tables. Verified applied: RLS on, anon/authenticated grants removed, Data API no longer returns rows.

**`public.spatial_ref_sys`** — **cannot be secured by the `postgres` role in this project**, so it remains handled by grants/exposure controls and the advisor finding is documented as a false positive:

- The table is owned by `supabase_admin` (extension-created). The `postgres` role here is **not a superuser** (`rolsuper = false`, `rolbypassrls = true`) and is not the grantor of the anon/authenticated grants (`supabase_admin` is). PostgreSQL `REVOKE` only removes grants made by the current user, so `REVOKE ALL ... FROM anon, authenticated` **silently no-ops**; `ALTER TABLE ... ENABLE ROW LEVEL SECURITY`, `ALTER TABLE ... OWNER TO`, and `CREATE POLICY` all fail with `must be owner of table spatial_ref_sys`. `SET ROLE supabase_admin` is denied.
- This is tracked upstream as an unresolvable false positive: supabase/supabase#47206 (open) — the Security Advisor flags `spatial_ref_sys`, users cannot enable RLS on it, and the Supabase team is excluding extension-owned tables from the lint.
- The table contains only public EPSG/SRID reference data (no PII, no tenant data). PostGIS functions that read it (`st_transform`, `addgeometrycolumn`, `get_proj4_from_srid`, `updategeometrysrid`) are SECURITY INVOKER, so a deny-all RLS would break them for API roles anyway.
- The migration ships a best-effort `REVOKE` for `spatial_ref_sys` (guarded, idempotent): it takes effect wherever `postgres` owns the table or is the grantor (self-hosted Supabase, the local-db profile where postgres is a superuser), and is a harmless no-op on hosted Supabase.

Both changes ship as Alembic migration `002_secure_internal_tables` (idempotent, guarded for role/table existence so it also runs on the local-db profile).

## Alternatives Considered

| Alternative | Why Rejected |
|-------------|-------------|
| Enable RLS + SELECT-only policy on `spatial_ref_sys` | PostGIS functions are SECURITY INVOKER, so a deny-all RLS would break them for API roles; a SELECT policy would work but forces RLS onto an extension-owned table. Supabase tracks this exact scenario as a false positive and is excluding extension-owned tables from the lint (supabase/supabase#47206): "forcing RLS onto extension-managed tables like spatial_ref_sys violates the PostGIS ownership paradigm and risks breaking future extension upgrades." |
| Ignore both findings | `alembic_version` is genuinely exposed (publicly writable via Data API) — not ignorable. |
| Move PostGIS to the `extensions` schema (`ALTER EXTENSION postgis SET SCHEMA extensions`) | Advisor's own remediation for `0014_extension_in_public`, but relocating an extension can break existing spatial queries and the app's `GEOGRAPHY` columns; too risky for a hackathon prototype. |
| Remove `public` from Exposed Schemas in API settings | Too broad — would disable the Data API for the whole project, including auth-adjacent flows. |
| Dashboard-only change (no migration) | Violates the project rule that all security changes must be reproducible and committed through the repository migration system. |

## Consequences

- `alembic_version`: anon/authenticated get zero rows; the Data API returns 401/403 for it. Alembic (postgres, bypasses RLS) and service_role are unaffected — future migrations and backend startup work unchanged.
- `spatial_ref_sys`: the advisor finding **remains in the dashboard** on hosted Supabase until Supabase ships the lint exclusion for extension-owned tables (supabase/supabase#47206). Exposure is limited to public EPSG reference data; the app never reads it through API roles (frontend: auth only; backend: postgres). If a future feature needs SRID lookups via the Data API, add a SELECT-only policy or re-grant SELECT.
- The migration's `REVOKE` for `spatial_ref_sys` is best-effort: effective on self-hosted/local-db environments, no-op on hosted Supabase.
- Downgrade of migration 002 restores the prior (insecure) grants and disables RLS — standard Alembic revert semantics; grant restoration is guarded so it cannot fail on objects whose grants postgres cannot re-grant.

## Evidence

- Replicated `rls_disabled_in_public` lint (from `packages/pg-meta/src/sql/studio/advisor/lints.ts`): exactly two findings, `alembic_version` and `spatial_ref_sys`; all application tables already have RLS enabled.
- `information_schema.role_table_grants`: full `arwdDxtm` for anon/authenticated on both tables; grantor for `spatial_ref_sys` is `supabase_admin`, for `alembic_version` is `postgres`.
- `pg_roles`: `postgres` has `rolsuper = false`, `rolbypassrls = true`; `service_role` has `rolbypassrls = true`.
- Data API probe with anon key: HTTP 200 on `/rest/v1/alembic_version` and `/rest/v1/spatial_ref_sys` before the fix; 401/403 on `alembic_version` after.
- `pg_proc.prosecdef = false` for `st_transform`, `addgeometrycolumn`, `get_proj4_from_srid`, `updategeometrysrid`.
- Direct tests: `REVOKE ALL ON public.spatial_ref_sys FROM anon` returns OK but leaves the ACL unchanged (grantor is `supabase_admin`); `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` / `OWNER TO` / `CREATE POLICY` fail with `must be owner of table spatial_ref_sys`; `SET ROLE supabase_admin` denied.
- supabase/supabase#47206 (open): Security Advisor flags `spatial_ref_sys` as RLS-disabled; Supabase team plans to exclude extension-owned tables from the lint.
- Supabase docs, `0013_rls_disabled_in_public`: remediation is `ALTER TABLE ... ENABLE ROW LEVEL SECURITY`; lint condition includes `has_table_privilege('anon'|'authenticated', oid, 'SELECT')`.
